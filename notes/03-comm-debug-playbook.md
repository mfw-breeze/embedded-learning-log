# 串行通信异常排查方法论（I2C / SPI）

**日期**：2026-11-11
**来源**：两次真实故障复盘后总结，配合 [001](../pitfalls/001-i2c-data-65xxx.md) 和 [002](../pitfalls/002-spi-write-read-mismatch.md) 一起看

## 一句话总结

**先证明"数据通路是通的"，再怀疑"数据内容对不对"；而证明内容对不对的唯一办法是"用已知答案对照 + 写后回读"。**

两次故障的共同点：屏幕上的数据，都不是我以为的那个数据——一个是显示层的符号问题，一个是"写成功"这个假象本身不成立。

## 分层定位

| 层 | 关注点 | 失败表现 |
|---|---|---|
| 物理层 | 供电、共地、杜邦线、上拉、引脚复用 | 全 0x00 / 全 0xFF |
| 链路层 | 时钟模式、速率、位序、CS 时序、地址、ACK | ID 错、偶发错位 |
| 协议层 | 命令码、寄存器地址、等待时序、写保护位 | ID 对但读不出、写不进 |
| 数据层 | 类型/符号、字节序、量程换算、校验 | 数值离谱但"像个数" |

**原则**：永远从"身份寄存器"开始（`WHO_AM_I` / JEDEC ID）。能读到正确 ID，就一次性证明前三层都通。

## 五个必做动作

1. 先读 ID，建立链路基准
2. 划分收发边界（波形 / 回环测试）
3. 用已知答案对照（读恒定寄存器）
4. **写必须回读**（`memcmp`，不是"没报错就是成功"）
5. 所有等待有超时，超时返回错误码

## 现象 → 病因 速查

| 现象 | 优先怀疑 |
|---|---|
| 全 0x00 / 全 0xFF | 没通信：接线、共地、CS、上拉、地址 |
| 有 ID 但错位 | 时钟模式、位序、采样沿 |
| 数据成批 65xxx | 有符号/无符号（零扩展 vs 符号扩展） |
| 量级差 2 的倍数 | 量程/灵敏度配置没生效 |
| 数据有规律递增 | 读到命令回显，或旧数据未擦 |
| 写后读不变 | 未擦除、写保护、WEL 没置位、地址错 |
| 复位后第一次正常 | 事务没收尾（CS/STOP）、状态机没复位 |

## 让代码"可排查"

```c
/* 反例：从机不响应就永远卡死，OLED 停在最后一帧 */
while (I2C_CheckEvent(I2C2, EVT) != SUCCESS);

/* 正例 */
uint32_t timeout = 10000;
while (I2C_CheckEvent(I2C2, EVT) != SUCCESS) {
    if (--timeout == 0) return ERR_TIMEOUT;
}
```

## 面试可能问什么

- 你做数据通信时，如果收发异常会怎么排查？（用本笔记的分层表回答）
- 怎么证明是通信问题而不是应用逻辑问题？（最小可复现程序 + 二分）
- I2C 和 SPI 你怎么选？（设备数、速率、引脚成本）
- 偶发失败怎么定位？（相关性分析 + 环形日志 + 降速复测 + 逻辑分析仪长触发）
